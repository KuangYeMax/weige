## 根因：出图质量忽好忽离谱 = 每次全新随机 seed + 模型高方差 + 重试预算小

- `BailianImageProvider.generate`（image_generation/bailian.py:219）每次调用 `seed = random.randint(0, 2**31-1)`，虽传给 wan2.7-image 但每次随机 → 等同于每次重新摇骰子；seed 从不持久化，好图无法复现（regen 写进 manifest 的 seed 也不复用）。
- wan2.7-image i2i（参考图）方差大：同参考图+提示词，不同 seed 结果天差地别（颜色/数量/姿态/结构漂移），属扩散模型+i2i 固有特性。
- 一致性校验是唯一兜底（consistency_check.py，视觉模型比对；调用异常时 `consistent=True` 放行），但自动调度 `consistency_check_max_retries=1` → 每编号最多 2 次机会，都歪就 needs_review（正是 444/666 挂因）。
- 手动"重新生成"只是再摇一次骰子 → 有时中。不是修复，是概率+多试几次。
- BUG：`dispatch_scheduler.py:180` 调度生成用 `aspect_ratio="3:4"`（1536*2048 竖图），但 `dispatch_regen_functions._regenerate_image_only` 用 `"1:1"`（2048*2048 方图）→ 重生成画幅与原批次不一致。
- 自动重试还会换 scene/shot_type（dispatch_scheduler.py:170-172），连提示词都变，非纯重摇。
- 非"卡住"：有 `_GENERATION_LOCK = Semaphore(1)` 全局串行所有 provider 调用（含 workbench 对比），是吞吐串行而非挂死。

**建议（待用户确认再改）**：① 调高 `consistency_check_max_retries`（如 3~5）让自动多摇几次少进 needs_review；② 锁 seed 可复现好图；③ 试关 `bailian_thinking_mode` 降方差；④ 修 3:4/1:1 不一致。

## 推送仓库的认证约束（踩坑记录）
- 本机 git remote 为 `https://github.com/KuangYeMax/weige.git`（HTTPS），凭据管理器 GCM 在非交互式 shell 下无法弹登录框（`/dev/tty` 不可用），且环境无 `GH_TOKEN`、无缓存凭证 → `git push` 直接失败。
- **可行做法**：让用户提供一次性 GitHub PAT（classic，需 `repo` 权限），用内联 URL 推送：`git push "https://<TOKEN>@github.com/KuangYeMax/weige.git" main`。推送后 `git remote get-url origin` 确认仍是干净 HTTPS（token 不进 config），并 `git credential reject` 清理，建议用户随后撤销该 token。
- 不要尝试交互式凭据弹窗或依赖 GCM 缓存；每次推送都需重新要 token。

### 本沙箱可用的"持久化 token"方案（已验证）
- GCM 在非交互式 shell 下无法弹窗（`/dev/tty` 不可用），`git credential approve` 存了也无法在 push 时读回（仍走提示框失败）。
- **可行且已验证**：把 token 直接写进 remote URL（存于本地 `.git/config`，不进版本库）：
  `git remote set-url origin "https://x-access-token:<TOKEN>@github.com/KuangYeMax/weige.git"`
  之后 `git push origin main` / `git fetch origin` 自动带认证，无需再发 token。
- 副作用：token 会以明文出现在 `git remote -v` 输出与 `.git/config`；`.git/config` 不会被提交。用户想移除可 `git remote set-url origin https://github.com/KuangYeMax/weige.git`。
- **沙箱缺陷**：`git fetch`/`git update-ref` 对 `packed-refs`（跟踪引用）的写入不落盘 → 本地 `origin/main` 跟踪引用会一直显示陈旧值（如 2a24a8d），`git status` 误报 "ahead N"。以 `git ls-remote origin main` 为准（权威），不靠 `git log origin/main..HEAD`。这不影响推送/拉取实际功能。

**最终结论（开讲述人复测后）**：开讲述人后微信 UIA 仍 `children=0`、`descendants(全部后代)=0`、按 control_type 找 Edit/Button/List/Custom 全空、yinkaowen uiautomation 同样空 → **4.1.1.19 完全不暴露 UIA 控件树，连讲述人都无效**。根因是版本本身未实现 Qt UIAutomation 接口，非环境配置问题（已排除"无障碍未激活"和"窗口不可见"两个假设）。「开讲述人→跑通→关→再测」逻辑链在第一步即断（开了都没用），任务B(验证关讲述人)前提不成立。**必须升级微信**。库源码有 `version<4.1.9` 版本分水岭、issue#147 是 4.1.6.14 的 UIA 问题 → **用户选定 4.1.9.57**。安装包下载自 `iibob/wechat-win-archive`(GitHub release，带 SHA256 签名校验)，存 `D:\WeChatInstallers\WeChatWin_4.1.9.57.exe`（另备 4.1.6.46 避开 issue#147 的 .14）。升级(卸载4.1.1.19→装4.1.9.57→重新登录)由用户亲自操作，完成后重跑 `scripts/probe_env.py` 验证 UIA 可用再进 Step 1。讲述人静音方案已验证可用(pycaw 单独静音 narrator 进程 + SAPI SpVoice Volume=0 双保险)，升级后若仍需讲述人激活可复用。

**重测后的决定性发现（微信升级 4.1.9.57 后）**：升级后重跑探针仍 NotFoundError；开讲述人后 `children=1~2`、`descendants=1`、class_name 仍 `Qt51514QWindowIcon`（未变 `mmui::MainWindow`）→ UIA 仍未激活。查 pyweixin 官方 `Weixin4.0.md` + issue#84 得出**决定性结论**：**微信 4.0.6+ 主动屏蔽 UIAutomation**（Qt 属性 `WA_MSAADisabled` / 重写 Qt 控件，inspect.exe/spy++ 也看不到内部 UI 结构）；**讲述人激活方式已失效**（作者原话"目前使用讲述人的方式来使UI树可见的方式已经失效"）；且是**账号级限制**（"微信更新后无法获取UI树，无论讲述人还是注册表都无效，但切换不同账号后又会可见"——微信按账号评估限制 UIA）。作者给唯一可行解法：①换一个 UI 树可见的账号；②把受限账号拿到另一台"UI 树可见"的电脑登录后再登回（缓存机制，不保证）。OCR 太慢、Hook 封号——都不适合 RPA。**结论：当前微信账号的 UIA 被微信限制，pyweixin/UIA 路线对当前账号走不通**，需用户决策方向。注意：之前判断"4.1.1.19 版本本身不暴露UIA"需修正——实为账号被限，与版本无关；升级到4.1.9.57无效印证了这点。

**换账号验证结果（账号B，4.1.9.57）**：仍 3通过6失败，第4步 NotFoundError，class_name 仍 Qt51514QWindowIcon。至此三变量（版本 4.1.1.19→4.1.9.57、账号 A→B、讲述人 开/关）全部试过，UIA 控件树在这台机器上始终不暴露 → **不是账号问题、不是版本问题、不是讲述人问题，是这台机器/这个微信安装被微信在底层屏蔽了 UIA**。pyweixin/UIA 路线在当前环境彻底走不通，原任务前提「换成 UIAutomation 控件定位」在当前环境无法实现，需与用户重新对齐方向（换机器验证设备级 / 放弃UIA在坐标方案上做自检护栏 / OCR辅助 / 完整报告）。

## 外部 AI 评审 wechat-sender-refactor-plan.md（4 硬伤 + 7 中等问题，全部采纳，仅改文档未改代码）

**采纳要点（已落到文档）**：
- 硬伤1：身份校验废除「截图 pHash/像素比对 + 首发建基准」（pHash 不判文字相等、基准会固化错误成 fail-confident）→ 改 OCR 精确判等；独立聊天窗口+`GetWindowText` 方案作为「优先实测、待验证」更优解。

- 硬伤3：无人值守三杀手 → DPI 从「仅记录」升为拦截+启动 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`；补 `OpenInputDesktop`+截图非黑 的桌面可交互检测；版本检查改运行期周期复检+热降级+关自动更新；统一 skip(可自愈)/degrade(硬失效) 语义（原文档 §5 与验收标准自相矛盾）。
- 硬伤4：`verify_remark` 与后台发送抢同一微信窗口 → 共用 `_SEND_LOCK`，verify_remark 拿不到锁返回「系统正忙」。注：当前代码尚无任何锁，落实时务必让二者共用一把。
- 中等问题：`_select_impl` 每次 send 重跑自检会重复发测试消息→自检启动跑一次并缓存；`send()` 多图失败不报进度→异常携带已成功条目+manifest per-item；缺 `open_chat`→一次定位锁内连发；搜索栏定位不可靠/`FRIEND_DUPLICATE` 常态→open_chat 精确选中等候项+OCR 校验；剪贴板全局资源→重试退避+粘贴前再确认+透明通道经 DIB 变黑故预检聚焦像素尺寸；验收#4（30轮不丢）原不可判定→用真验证使其可机判；文件传输助手验不到真风险→增补受控真实小号端到端。

## 真实环境冒烟调试（2026-07-29 晚，发现并修复 4 个真实 bug）

按用户指示「先做2（实测独立窗口）→ 再做3（真实冒烟）→ 测试通过后 commit」执行，过程中发现 4 个计划未覆盖的真实 bug，全部修复。

### Bug 1：搜索结果选错会话（消息发到群聊）
- **现象**：冒烟发送"文件传输助手"，消息发到了群聊"0845班坚毅战队"（86人群）
- **根因**：旧 `_search_and_open` 用「两次 enter 赌第一个搜索结果」，搜索结果第一个不是目标好友时就选错
- **修复**：`sender.py` `_search_and_open` 新增 OCR 精确选中——搜索后用 rapidocr 识别结果列表，找 `text==remark` 的项 click 选中；OCR 可用但没找到精确匹配时**直接抛 RuntimeError 返回 FRIEND_NOT_FOUND**（不再 fallback 到两次 enter，止血）；OCR 不可用（rapidocr 未装）才 fallback

### Bug 2：搜索框残留词导致搜错目标（消息发到"蝗虫"）
- **现象**：OCR 精确选中修复后，消息又发到了"蝗虫"会话
- **根因**：搜索框里有残留词"蝗虫"，`ctrl+a` 没真正全选清空，`ctrl+v` 没覆盖
- **修复**：`_search_and_open` 搜索前强制清空——`ESC`（微信清空搜索）+ 重新 click + `ctrl,a` + `delete` 三重清空

### Bug 3：force_foreground 时机问题（WorkBuddy 抢回前台）
- **现象**：OCR 截到的搜索结果区域是 WorkBuddy 左侧栏
- **根因**：`_search_and_open` 没在开头调 force_foreground，WorkBuddy IDE 抢回前台
- **修复**：`_search_and_open` 开头 + ESC 后重新 click 前，各调一次 `force_foreground(hwnd)`
- **附带**：`win32.py` `force_foreground` 加 rect<-1000 检查（窗口最小化到 -32000 时 MoveWindow 恢复）

### Bug 4：真验证截图范围错误（误判"无新增气泡"）
- **现象**：消息成功发到"零哥"，但真验证报告 `send_not_confirmed`（变化率=0.000）
- **根因**：`_screenshot_chat_bottom` 只截会话区底部（y=50%~85%），新消息在顶部（y≈172）
