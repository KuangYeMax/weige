## 排查：安生生待发任务 7d415fa6 卡在 needs_review

**任务**：`7d415fa6880e4e80b31f0af6335af6f2`，wx_remark=安生生，send_codes=[444,555,666,777]，countdown_days=3，trigger_at=2026-07-31T21:30Z。

**结论**：生成已正常跑完（05:21:55→05:26:32 本地，provider bailian/wan2.7-image），但 444 与 666 两张图**未通过一致性校验**（生成图 vs 原产品图差异大：牛的颜色/体态/纹样、马的数量/底座/配色/海浪）。系统为防发错货把整条置 `needs_review`，按设计不自动重发/重生成。服务进程健康（8000 监听 PID 23468），无需重启；重启对 needs_review 无效且会再卡同一致性校验。

**发现的实现缺口（重要）**：
- `POST /api/dispatch/{id}/retry-after-review`（`retry_dispatch_task_after_review`）只把 DB 任务状态置 `ready`，**不改 manifest 里逐编号 status**。而发送端 `_ready_send_items` 仅发送 manifest `status=="ready"` 的结果 → 当前直接点"人工复核后重投"，只会发 555/777，444/666 被静默跳过（任务却标记 sent）。
- 详情页 dispatch_detail.html 每个编号的"换图/重新生成/跳过"按钮是 disabled（标注"接口待补"），暂无法在 UI 单独救 444/666。
- 即便放行，trigger_at 在 07-31，调度器在那之前不会真正发出。

**后续**：待用户决定（A 改 manifest 把 444/666 置 ready 并改触发时间为现在全发；B 重生成 444/666；C 只发 555/777；D 不动）。此缺口建议作为 bug 修复：retry-after-review 应同步把 needs_review 编号（用户已确认）flip 成 ready，或前端逐编号审核。

## 根因：出图质量忽好忽离谱 = 每次全新随机 seed + 模型高方差 + 重试预算小

- `BailianImageProvider.generate`（image_generation/bailian.py:219）每次调用 `seed = random.randint(0, 2**31-1)`，虽传给 wan2.7-image 但每次随机 → 等同于每次重新摇骰子；seed 从不持久化，好图无法复现（regen 写进 manifest 的 seed 也不复用）。
- wan2.7-image i2i（参考图）方差大：同参考图+提示词，不同 seed 结果天差地别（颜色/数量/姿态/结构漂移），属扩散模型+i2i 固有特性。
- 一致性校验是唯一兜底（consistency_check.py，视觉模型比对；调用异常时 `consistent=True` 放行），但自动调度 `consistency_check_max_retries=1` → 每编号最多 2 次机会，都歪就 needs_review（正是 444/666 挂因）。
- 手动"重新生成"只是再摇一次骰子 → 有时中。不是修复，是概率+多试几次。
- BUG：`dispatch_scheduler.py:180` 调度生成用 `aspect_ratio="3:4"`（1536*2048 竖图），但 `dispatch_regen_functions._regenerate_image_only` 用 `"1:1"`（2048*2048 方图）→ 重生成画幅与原批次不一致。
- 自动重试还会换 scene/shot_type（dispatch_scheduler.py:170-172），连提示词都变，非纯重摇。
- 非"卡住"：有 `_GENERATION_LOCK = Semaphore(1)` 全局串行所有 provider 调用（含 workbench 对比），是吞吐串行而非挂死。

**建议（待用户确认再改）**：① 调高 `consistency_check_max_retries`（如 3~5）让自动多摇几次少进 needs_review；② 锁 seed 可复现好图；③ 试关 `bailian_thinking_mode` 降方差；④ 修 3:4/1:1 不一致。

## BUG 修复：开场语（wechat_opening_text）重启即丢

**现象**：用户在设置页保存开场语，当时发送生效，但服务重启后变空白。

**根因**：`app/api/settings.py` 的 `update_settings` 只把 `wechat_opening_text`（及 `wechat_send_interval_min/max`、`dispatch_image_provider`）写入内存中的 `Settings` 对象，**没有持久化到 `.env`**（对照 `update_api_keys` 有写 `.env` 逻辑）。`config.py` 里 `wechat_opening_text: str = ""` 是 `BaseSettings` 字段，默认从 `.env` 加载，而 `.env` 无该键 → 进程重启即回退默认空串。前端 5 秒定时刷新不覆盖编辑态，非前端问题。

**修复**：
- `app/api/settings.py`：抽出模块级 `_persist_env_value(key, value)`，带双引号包裹+转义（兼容换行/引号）；`update_settings` 在改动 `wechat_opening_text`/`wechat_send_interval_min`/`wechat_send_interval_max`/`dispatch_image_provider` 时同步写回 `.env`（`WECHAT_OPENING_TEXT` 等）。`send_window_start/end` 维持原注释的内存态、不持久化。
- `tests/conftest.py`：新增 autouse fixture `_isolate_settings_env_file`，把 `_ENV_PATH` monkeypatch 到 `tmp_path/.env`，避免测试污染项目根真实 `.env`（因 `client` fixture 的 `Settings()` 仍会读真实 `.env`）。

**验证**：`pytest tests/test_new_api.py::TestSettings` 2 passed；另写临时脚本验证 `_persist_env_value` 写入 `.env` 后 `Settings(_env_file=tmp)` 能正确读回（含引号、多行），未触碰真实 `.env`。

**遗留提醒**：目前仅 API Key 与本次修复的 4 个字段真正持久化；其余 `Settings` 字段（如 `consistency_check_max_retries`、`bailian_thinking_mode`、坐标等）仍为内存态，重启即丢——如需"保存即记住"，应同样接 `_persist_env_value` 或迁移到 DB。
