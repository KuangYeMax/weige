# 请评估以下「好评图生成锁种子」方案的可行性

## 一、背景

我有一个**微信好评图自动生成与群发系统**。后端 FastAPI，前端 Alpine.js。核心流程：

1. 上传产品原图 → 生成产品事实卡（AI 视觉分析，含主体关键结构、保真锁等约束）；
2. 用户在「待发列表」新建任务、配置参数（场景 scene、景别 shot_type、角度 camera_seed 等）；
3. 组装 prompt → 调用 **wan2.7（i2i 图生图）** 模型生成好评图 → 后处理调色；
4. 微信自动群发给不同好友（同一产品要发给多个不同客户）。

**当前生成管线的关键事实：**

- 每次调用 wan2.7 时，模型 **seed 由代码 `random.randint(0, 2**31-1)` 全新随机生成**（bailian provider 内部，约第 219 行），**不持久化、不读取外部值**。
- 系统另有**两个独立随机源**：`camera_seed`（控制角度/构图）、`scene`/`shot_type`（随机抽场景/景别，拼进 prompt 背景文字）。三者互不影响。
- **一致性校验**：用视觉模型比对「产品原图 vs 生成图」，主体（颜色/数量/结构）不一致则判失败；`consistency_check_max_retries=1`，一个编号最多生成 2 次，两次都失败进 `needs_review` 人工救火（校验 API 异常时默认判通过）。
- **现状痛点**：同一产品每次都是全新随机 seed，导致 wan2.7 对复杂/多主体商品（如牛摆件、5 匹马摆件）保真波动极大——有时主体正确，有时离谱（数量错、姿态飘），**忽好忽坏**。用户必须手动重新生成救火。简单单主体商品反而较稳。

## 二、目的

1. 让**同一产品的「主体」**在每次生成时都**稳定正确、可复现**，不再忽好忽坏；
2. 同时，同一产品群发给**不同微信好友**时，每张图的**场景、角度、陪衬物要各不相同**（像不同真人拍的不同好评），避免群发穿帮；
3. 降低人工重新生成救火的频率。

## 三、解决方案（用户方案：「锁定最后的种子」）

- 每个产品 metadata 增加 `current_seed` 字段，存「当前种子」。
- 正常生成（自动调度 / 待发）时使用该产品的 `current_seed` 去调 wan2.7；**若首次尚无 `current_seed`，则随机生成并写入**。
- **首次生成且通过一致性校验后，即把本次使用的 seed 锁定为 `current_seed`**（写回 metadata）。
- 若用户对生成的图不满意，手动点击「重新生成 / 换图」：系统抽一个**全新** seed 生成，若用户满意（或再次通过校验），则把新 seed 存为 `current_seed`，**覆盖旧值**——即永远锁定「上一次生成成功的那个种子」，**无需单独的「锁定」按钮**。
- **只锁定模型 seed（决定主体），`scene`（场景）、`camera_seed`（角度）、图片中的其他物品一律不锁定**，每次生成照常随机变化 → 主体永远正确、场景角度各异、不穿帮。
- **自动调度重试阶段：复用同一 `current_seed`（仅变化 scene/camera_seed），不换种子**；只有用户主动重生成才换 seed；两次都没过（`needs_review`）时不修改 `current_seed`。

## 四、请评估的问题

1. **可行性（最关键）**：wan2.7 这类 i2i 图生图模型，在「**相同 seed + 相同参考图 + 相同核心 prompt（含主体描述）+ 不同 scene/camera_seed**」下，主体（如牛）是否能被**稳定复现**？seed 是否真的只影响随机噪声初始分布、而不改变主体身份？请依据扩散模型 / 图生图原理判断，并指出**前提条件**（如是否需要同时固定除 seed 外的采样步数、采样器、参考强度 / controlnet 等参数；scene/camera 的变化是否会被模型重新演绎主体而致偏离）。
2. **风险与副作用**：锁 seed 后，主体在不同背景下的**光影 / 透视融合是否可能僵硬**（像把同一头牛 P 到不同背景）？scene/camera 的变化是否会**反过来破坏主体保真**（例如新角度下牛的姿态被模型重新生成而偏离种子锁定的形态）？
3. **落地建议**：当前 bailian provider 每次内部随机 seed 且不暴露参数，要支持「**外部传入 seed**」需要改哪些点？`current_seed` 应持久化在何处、何时写回？自动重试「复用 seed 只变 scene/camera」在实现上是否安全、是否会与一致性校验逻辑冲突？
4. **替代 / 补充手段**：在「锁种子」之外，是否还应配合「提高重试次数、关 thinking_mode 降方差、生图前人工确认事实卡」等以进一步降低 `needs_review` 率？给出优先级建议。

- **最关键的前提假设**是什么（例如：必须验证「同 seed 确实能复现主体」）？
