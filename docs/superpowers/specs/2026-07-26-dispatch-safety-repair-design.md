# 调度文案与微信发送安全修复设计

## 目标与边界

修复已审计确认的好评文案空内容、微信坐标、会话校验、发送状态和配置契约问题。发送自动化只允许完成可观测的本地输入提交；它不把无法从当前 Win32 管道验证的微信送达结果标记为 `sent`。

本次不改变产品、图片生成或既有调度触发逻辑，不修复现有 `z-image-turbo` 测试基线失败，也不引入 OCR、UIA 或新的第三方依赖。

## 文案生成

`generate_review` 和 `generate_content` 的边界保证返回非空、去除首尾空白的文案。禁词重试耗尽时，若配置的回退文案为空，使用内置非空回退；调度器在写入 `content.txt` 前再次校验。任何无法获得有效文案的情况抛错，使生成任务按现有失败路径处理，而不落盘空文件。

现有硬禁词继续使用长度至少两个字符的完整词组匹配。默认“小不足”只保留物流、包装或服务类的温和描述。

## 微信本地提交

发送入口拒绝空白备注名及空消息载荷。输入框坐标统一从窗口底边向上计算，X 坐标仍相对窗口左边。剪贴板、找窗、前台、会话校验和本地快捷键调用的异常均向上抛出。

会话校验采用 fail-closed：取得的主窗口标题必须在标准化后与目标备注完全相等；任何空标题、包含匹配、重名或无法读取当前会话名均终止发送。该策略宁可拒绝正确会话，也不在无法证明目标时发送。

`Clipboard.SetImage` 保持为图片剪贴板路径。随机间隔继续使用现有可配置的 1-3 秒默认区间。

## 状态机与人工确认

真实发送任务的状态扩展为 `ready -> sending -> awaiting_confirmation -> sent`。成功完成所有本地提交后进入 `awaiting_confirmation`，而不是 `sent`。操作人员在 Windows 微信上人工确认消息确已显示在正确会话后，通过受限 API 将任务标记为 `sent`。dry-run 任务不经过微信发送，直接进入独立终态 `dry_run_complete`，不能由人工确认接口改成 `sent`。

发送过程中任何异常、缺失内容、缺失图片，或在非 Windows 平台尝试实际发送时，任务返回 `ready` 并记录失败原因。启动恢复同时把孤立的 `generating` 和 `sending` 任务恢复为可重试状态；`awaiting_confirmation` 不自动重发，以避免重复消息。

人工确认 API 只接受当前状态为 `awaiting_confirmation` 的任务。它不执行发送，也不允许从 `ready`、`sending` 或其他状态跳到 `sent`。

## 配置

保留 hard/soft 禁词分层，并提供 `review_forbidden_words` 作为兼容配置入口，映射到硬禁词列表。`.env.example` 记录 review、微信坐标、间隔和模型配置；列表值使用 JSON 数组。

## 验证

新增 mock 测试覆盖：空回退不落盘、会话标题必须精确匹配、输入坐标、空载荷与剪贴板异常、非 Windows 不会标记成功、缺文件回退 ready、`awaiting_confirmation` 的转换和人工确认守卫。全量 pytest 必须保持仅有四个指定的 `z-image-turbo` 基线失败。

Windows 现场验收：确认目标会话标题格式确实可严格读取；验证图片以图片气泡出现；验证坐标、焦点、登录失效和断网行为；人工确认入口只在消息出现在正确会话后使用。
